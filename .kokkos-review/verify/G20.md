# Verify G20

### F-G20-1
VERDICT: CONFIRMED (latent)
reason: norm_functor stores `int norm` and takes an `int norm_` constructor argument (fft3d_kokkos.cpp:157-159). The caller passes `FFT_SCALAR norm = plan->norm` (=1/(nfast*nmid*nslow) < 1), which truncates to 0, so every scaled backward FFT output becomes 0. fft2d_kokkos.cpp has the same `int norm` in its norm_functor (~lines 155-159). Both are unreachable from compute fft/grid/kk, which passes scaled=0 and only does FORWARD transforms. The CPU code uses FFT_SCALAR norm.
fix: fft3d_kokkos.cpp:157 and :159, and fft2d_kokkos.cpp at the same lines of its norm_functor: change `int norm;` to `FFT_SCALAR norm;` and `int norm_` to `FFT_SCALAR norm_`.

### F-G20-2
VERDICT: CONFIRMED (latent)
reason: In the KISS branch, the slow-axis FFT runs out of place into a fresh d_tmp and sets `d_data = d_tmp` (fft3d_kokkos.cpp:353-360). d_out is written only by post_plan (lines 365-372). post_plan is nullptr only when permute==2 and out == third layout (lines 550-559). In that case d_out never receives the slow-axis result, and the norm functor then scales stale data. This is unreachable from compute fft/grid/kk, which uses permute=0 (compute_fft_grid_kokkos.cpp:543-546). The 2D twin is F-G19-5.
fix: fft3d_kokkos.cpp, after line 360 `d_data = d_tmp;` (KISS branch): add `if (!plan->post_plan) Kokkos::deep_copy(Kokkos::subview(d_out,std::make_pair(0,plan->total3)),Kokkos::subview(d_tmp,std::make_pair(0,plan->total3)));`. total3 equals the out size when post_plan is null.

### F-G20-4
VERDICT: CONFIRMED (latent)
reason: In the collective path, commringlist is built from the GLOBAL Allreduce counts (remap3d_kokkos.cpp:~545-578), so commringlen>0 even on a rank where nsend==nrecv==0. All plan arrays, selfcommringloc and nsend/nrecv are set only inside `if (nsend || nrecv)` (line 594). The plan comes from `new struct remap_plan_3d_kokkos<DeviceType>;` (line 295), which default-initialises and leaves the POD members indeterminate. The store-send loop (line ~660), the store-recv loop (~706) and `plan->sendcnts[plan->selfcommringloc]` (~763) run unconditionally and write through garbage pointers on such a rank. If the rank is in the ring but has no self overlap, selfcommringloc can also be -1. The CPU remap3d builds the ring from its own send/recv procs (src/FFT/remap3d.cpp:456-554), so it has no such case. This is unreachable today, because compute fft/grid/kk forces collective_flag=0 (compute_fft_grid_kokkos.cpp:538).
fix: remap3d_kokkos.cpp:295: `plan = new struct remap_plan_3d_kokkos<DeviceType>();`. Value-initialisation zeroes the POD members, since the struct has no user-provided constructor. Also wrap the store-send/store-recv loops, the d_sendbuf allocation and the `if (plan->sendcnts[plan->selfcommringloc])` self block (lines ~657-772) in `if (nsend || nrecv) { ... }` (with `else plan->self = 0;`), and guard the self block with `plan->selfcommringloc >= 0 &&`.

### F-G20-5
VERDICT: CONFIRMED (latent)
reason: Create allocates send_offset/send_size/packplan and recv_offset/recv_size/unpackplan together whenever (nsend||nrecv) (remap3d_kokkos.cpp:594-655). Destroy frees the send group only `if (plan->nsend)` and the recv group only `if (plan->nrecv)` (lines 836-846), so a receive-only or send-only rank leaks the other group. On an idle rank (nsend=nrecv=0), nsend/nrecv and sendcnts/rcvcnts/sdispls/rdispls are never assigned. They are indeterminate, because the plan is `new`ed without value-initialisation. If commringlen==0, realloc(…,0) may also return a non-null pointer, and then free(plan->sendcnts) is called on garbage. The path is collective-only, so it is unreachable today.
fix: remap3d_kokkos.cpp:295: value-initialise the plan (`new ...<DeviceType>();`, as in F-G20-4). In destroy, lines 836-846: replace `if (plan->nsend)` and `if (plan->nrecv)` with a single `if (plan->nsend || plan->nrecv) { free send_offset, send_size, packplan, recv_offset, recv_size, unpackplan }`. free(nullptr) is safe after value-initialisation.

### F-G20-6
VERDICT: CONFIRMED (latent)
reason: unpack_3d_permute1_n_functor (pack3d_kokkos.h:295) uses `in = instart + nqty*fast*nstride_plane`. nstride_plane is already nqty-scaled (`nqty*out.ksize*out.jsize`, remap3d_kokkos.cpp permute==1 branch), and CPU pack3d.h:176-179 advances `instart += nstride_plane` per fast index. The sibling permute1_1/permute1_2 functors (lines 185, 238) correctly use `fast*nstride_plane`. With nqty>=3 the functor writes to wrong or out-of-bounds locations. All FFT remaps use nqty=2, so the path is unreachable today.
fix: pack3d_kokkos.h:295: `int in = instart + fast*nstride_plane;`.

### F-G20-8
VERDICT: CONFIRMED (low, build-configuration only)
reason: The KOKKOS_ENABLE_CUDA branch (fftdata_kokkos.h:43-55) and the SYCL branch (72-84) undefine FFTW, FFTW3 and MKL but not FFT_KOKKOS_NVPL. The HIP branch does undefine it (lines 63-65). With -DFFT_KOKKOS_NVPL on a CUDA build, FFT_KOKKOS_KISS gets defined (no CUFFT), but the #elif chain at 135-150 selects NVPL first: FFT_KOKKOS_DATA = fftw_complex and FFTW_API are set. kissfft_kokkos.h is then included (line 268) and uses `.re/.im` on that type, which fails to compile. fft2d/fft3d_kokkos.cpp would also take the `FFT_KOKKOS_FFTW3 || FFT_KOKKOS_NVPL` host-FFTW branch on device data. With both NVPL and CUFFT defined, NVPL still wins the data-type chain ahead of CUFFT. This is a compile-time failure, not silent wrong results.
fix: fftdata_kokkos.h: in the CUDA branch (after line 51) and the SYCL branch (after line 80), add `# if defined(FFT_KOKKOS_NVPL)\n#  undef FFT_KOKKOS_NVPL\n# endif`, mirroring lines 63-65 of the HIP branch.

### F-G20-9
VERDICT: CONFIRMED (high: silent wrong results on the default GPU FFT backend)
reason: kiss_fft_alloc_kokkos allocates a single `st.d_scratch` of length p_max per plan state (kissfft_kokkos.h:512). kiss_fft_functor copies `st` by value, but the View copy aliases the same allocation (fft2d_kokkos.cpp:177-199, fft3d_kokkos.cpp:179-201). Each work item i of `parallel_for(total/length, f)` (fft2d_kokkos.cpp:259,308,756-765; fft3d_kokkos.cpp:261,310,359,965-980) runs an independent 1d FFT at offset i*length. Every one of them reaches kf_bfly_generic for any radix not in {2,3,4,5} (kf_work switch, lines ~434-440). That function writes `d_scratch(q1)` (lines 380-406) and then reads `d_scratch(0..p-1)` back, so concurrent work items overwrite each other's scratch: a data race that gives wrong FFT values. kf_factor (lines 458-485) emits p>5 for any prime factor >=7, e.g. nx = 7, 11, 13, 14, 21, 22, 26, 28, 49, 98... This is reachable from compute fft/grid/kk on any non-2,3,5-factorable grid dimension, which compute_fft_grid_kokkos.cpp:479-487 only warns about. KISS is the forced default on CUDA, HIP and SYCL builds without CUFFT/HIPFFT/MKL_GPU (fftdata_kokkos.h:53-55,69-71,82-84) and on host builds with no FFT library. On the Serial backend there is no concurrency, so results are correct there. They are wrong on OpenMP and every GPU backend. The data dependency is real: scratch[q] for q>=1 is read in the inner loop after other threads may have overwritten it. The cfg_slow==cfg_fast aliasing when nslow==nfast (fft2d_kokkos.cpp:625-628) only widens the sharing. The CPU code allocates scratch per call (KISS_FFT_TMP_ALLOC, src/FFT/kissfft.h:345), so it is private.
fix: give each 1d FFT its own scratch slice.
 (1) kissfft_kokkos.h:139-147: add `int p_max;` to kiss_fft_state_kokkos. In kiss_fft_alloc_kokkos (line 511-512), set `st.p_max = kf_factor(...)` and drop the shared `st.d_scratch` allocation (set `st.p_max = 0` when nfft==0).
 (2) Add a scratch argument to the call chain: `kiss_fft_kokkos(cfg, d_fin, d_fout, offset, d_scr, scr_offset)` -> kiss_fft_stride -> kf_work (forward it in the recursive call) -> kf_bfly_generic. In kf_bfly_generic, replace `d_scratch(q1)`, `d_scratch(0)` and `C_MUL(t,d_scratch,q,...)` with indices `scr_offset+q1`, `scr_offset+0` and `scr_offset+q` on d_scr.
 (3) kiss_fft_functor (fft2d_kokkos.cpp:177-199, fft3d_kokkos.cpp:179-201): add a member `t_FFT_DATA_1d_um d_scr`. Its operator() calls `kiss_fft_kokkos(st,d_data,d_tmp,i*length,d_scr,i*st.p_max)`. At each call site, next to the existing per-call `d_tmp` allocation, allocate `typename FFT_AT::t_FFT_DATA_1d d_scr(Kokkos::view_alloc("fft:kissscratch",Kokkos::WithoutInitializing), (size_t)(total/length)*MAX(1,cfg.p_max));` and pass it to the functor. Do the same in fft_*_1d_only_kokkos.
 (A less invasive interim guard: in compute_fft_grid_kokkos.cpp:479-487, under FFT_KOKKOS_KISS, turn the "not factorable by 2,3,5" warning into error->all.)
