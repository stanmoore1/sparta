### F-G21-3
VERDICT: REFUTED
reason: buffers are never undersized by a small factor: every use only grows (`if (extent < X_extra) realloc`), and the kernels detect capacity overflow and set d_retry; with retry=no the host then errors "Ran out of space in Kokkos collisions, increase react/extra" (collide_vss_kokkos.cpp:921-925). So react/extra<=1 yields a clean error, not memory corruption. (Input validation `react_extra >= 1.0` would be nice but is not a defect.)
side-observation (not part of this finding, worth a separate check by the collide group): collide_vss_kokkos.cpp:798,1230,1974,2479,3154 apply react_extra only `if (react_retry_flag)`, while doc/package.txt:85-101 says react/extra is the mechanism for retry=no and is ignored for retry=yes, and update_kokkos.cpp:685 uses `!react_retry_flag`. So in the default mode (retry=no) collide ignores react/extra entirely (extra_factor=1.0) and the "increase react/extra" error message is useless advice. Long-standing upstream (since PR #558 merge). Possible fix: `if (!sparta->kokkos->react_retry_flag)` at those lines.

### F-G21-4
VERDICT: CONFIRMED
reason: bundled Kokkos is 5.2.2 (lib/kokkos/CMakeLists.txt:142-144). Kokkos::Experimental::{HIP,HIPHostPinnedSpace,SYCL,SYCLHostUSMSpace} exist only as deprecated aliases inside `#ifdef KOKKOS_ENABLE_DEPRECATED_CODE_5` (Kokkos_Declare_HIP.hpp:24-37, Kokkos_Declare_SYCL.hpp:24-36). Kokkos_ENABLE_DEPRECATED_CODE_5 defaults ON (kokkos_enable_options.cmake:33) and SPARTA forces deprecation warnings OFF (src/KOKKOS/CMakeLists.txt:16), so the default build compiles silently; a HIP/SYCL build with -DKokkos_ENABLE_DEPRECATED_CODE_5=OFF (or Kokkos 6 / an external Kokkos built without it) fails to compile. Latent, low severity. OpenMPTarget branches (kokkos_type.h:200-216,270-...) are dead for Kokkos 5 but harmless. Only kokkos_type.h uses these names.
fix: src/KOKKOS/kokkos_type.h: replace `Kokkos::Experimental::HIP` -> `Kokkos::HIP` (:192, AtomicDup :253,:258), `Kokkos::Experimental::HIPHostPinnedSpace` -> `Kokkos::HIPHostPinnedSpace` (:211), `Kokkos::Experimental::SYCL` -> `Kokkos::SYCL` (:197, AtomicDup :263,:268), `Kokkos::Experimental::SYCLHostUSMSpace` -> `Kokkos::SYCLHostUSMSpace` (:213). The non-Experimental names exist since Kokkos 4.0, so external Kokkos 4.x is unaffected. (grep the file for any other `Experimental::HIP`/`Experimental::SYCL`.)

### F-G21-6
VERDICT: PLAUSIBLE
reason: correct that destroy_kokkos(TYPE data, ...) (memory_kokkos.h:107,301) takes the DualView by value, so `data = TYPE()` only drops the local copy and the caller's DualView keeps the allocation until the following create_kokkos assigns a new one (create_kokkos:41 `data = TYPE(name,n1)` constructs the new view before the old is released) -> transient old+new peak. Not a correctness bug: no dangling pointer (array set NULL, old buffer still referenced). Also the extra peak is often unavoidable anyway because callers keep separate device handles (e.g. compute_eflux_grid_kokkos.cpp: d_vector_grid/d_tally members hold the old device views until reassigned after create), so changing to by-reference alone does not remove the device-side peak. Same signature is used upstream (LAMMPS memory_kokkos.h). Low severity memory/efficiency issue only.
fix (optional): memory_kokkos.h:107 and :301 change `TYPE data` -> `TYPE &data` (all callers pass lvalues: members or `k_x.view_host()[i].k_view` elements); for full effect callers should also reset their d_ handles (e.g. `d_vector_grid = {};`) before create. Must re-verify ParticleKokkos custom-array paths (k_eivec/k_edarray...view_host()[i].k_view) still behave, since by-ref will now actually release those slot views.
