# Verify G16

### F-G16-1
VERDICT: CONFIRMED
reason: post_process_grid_kokkos writes into column m (subview(d_array_grid1,ALL,m)), but the result is read back from column jm1=nrhoindex[m]-1. These are equal only when the nrho args are c_ID[1] c_ID[2] ... in order (the usual c_ID[*] expansion). Simple scenario: two different post-processing computes each used as [1] (e.g. "c_a[1] c_b[1]", nrho_values=2). For m=1, j=1, so it reads column 0, which holds m=0's result: the nrho of species 1 is silently replaced by species 0's. A mixed order such as c_g[2] c_g[1] swaps them. The CPU code has the identical bug at compute_lambda_grid.cpp:522. (j>=1 always holds here, because a post-processing compute must be indexed, so there is no -1 out-of-bounds read.)
cpu-also: yes
fix: src/KOKKOS/compute_lambda_grid_kokkos.cpp:174-176 -> read column m: `l_nrho(i,k) = l_array_grid1(i,m);` (m is the loop int; capture a `const int mm = m;` for the lambda) and drop jm1 in that branch. Same change on CPU src/compute_lambda_grid.cpp:522: `nrho[i][k] = array_grid1[i][m];`.

### F-G16-2
VERDICT: REFUTED
reason: Every Kokkos per-grid compute that can supply temp (thermal/grid, grid, tvib/grid, sonine/grid, eflux/pflux, ...) allocates d_vector_grid with create_kokkos(...,nglocal) in reallocate(), which runs on every grid change. So its extent always equals grid->nlocal, which equals d_temp's extent (lambda/grid reallocate, line 442). Only fixes (ave/grid grow_kokkos) over-allocate, and that branch already takes a subview. The extent mismatch cannot occur with the existing styles. At most this is hardening.
fix: none required. Optional hardening: deep_copy from Kokkos::subview(ctempKKBase->d_vector_grid,std::make_pair(0,nglocal)), as the fix branch does.

### F-G16-3
VERDICT: REFUTED
reason: After the invoke, the fallback `return 0` fires only if d_vector_grid/d_array_grid is null or shorter than grid->nlocal. All Kokkos per-grid computes allocate exactly nglocal in reallocate(), which runs from init and on every grid change, so the only case left is nglocal==0 (a proc with no cells: data()==nullptr). In that case the host compute_one loops over 0 cells and the result is the reduction identity, which is correct. A stale-host-data reduction would need a compute whose device output is under-allocated, and none exists. The behavior is a latent hazard at most; the file's own CAVEAT comment documents the analogous particle case.
fix: none required. Optional: move the null/extent checks before the invocation, or on fallback clear INVOKED_PER_GRID so the host re-invokes.

### F-G16-4
VERDICT: CONFIRMED
reason: compute_count_kokkos.cpp:122 sets invoked_scalar in compute_vector(), and so does CPU compute_count.cpp:187. scalar_flag (nvalues==1) and vector_flag (nvalues>1) are mutually exclusive (compute_count.cpp:95-97), so stale-scalar misuse cannot happen. The only consumer of invoked_vector is library.cpp:462 (sparta_extract_compute), which then re-calls compute_vector every time. That is cheap because of the lasttally guard. Variable and fix ave/time use invoked_flag, not invoked_vector. The bug is real but has negligible impact.
cpu-also: yes
fix: src/KOKKOS/compute_count_kokkos.cpp:122 `invoked_vector = update->ntimestep;` (and src/compute_count.cpp:187 likewise).

### F-G16-5
VERDICT: CONFIRMED
reason: compute_per_grid_kokkos takes grid_kk->k_cells.view_device() and k_cinfo.view_device() without any grid sync, and the kernel reads d_cells[icell].nsurf/nsplit/isplit/lo/hi. On a second or later run, UpdateKokkos::setup (update_kokkos.cpp:368) does grid_kk->modify(Host,ALL_MASK) and then rebuilds d_csurfs/d_csubs from the current host data (wrap_kokkos_graphs), but it never sync(Device)s the cells. Update::setup -> output->setup(1) then invokes the compute (dump grid / fix ave/grid / variable at step 0). Nothing between those points syncs CELL_MASK; the per-step sync at update_kokkos.cpp:701 only runs inside the run loop. After a host grid change between runs (adapt_grid, balance_grid, fix ablate), the device cells are stale while csurfs is fresh: nsurf no longer matches the row_map, which gives wrong distances or out-of-bounds csurfs/csubs reads. The first run is safe because wrap_kokkos syncs everything. compute_property_grid_kokkos.cpp:111 and compute_dt_grid_kokkos.cpp:278 both do the sync this compute is missing.
fix: src/KOKKOS/compute_distsurf_grid_kokkos.cpp, immediately after line 127 (`GridKokkos* grid_kk = ...`) and before taking the views at 128-129, add `grid_kk->sync(Device,CELL_MASK|CINFO_MASK);` (same as compute_property_grid_kokkos.cpp:111).
