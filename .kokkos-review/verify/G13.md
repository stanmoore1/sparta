### F-G13-1
VERDICT: REFUTED
reason: Every consumer of dtremain/weight on a freshly added particle gets them set explicitly before use. The move reads dtremain only for flags other than PKEEP (update_kokkos.cpp:1244-1286). PINSERT emitters set dtremain (e.g. fix_emit_face_kokkos.cpp:374-375). Surf-reaction products have flag/dtremain/weight set at update_kokkos.cpp:1854-1857 and 2174-2177, which matches CPU update.cpp:1249-1251. collide_vss_kokkos.cpp:3009 overwrites the whole struct with *jpart. Particles created outside the move (create_particles, fix emit at start_of_step, collisions) have weight reset by pre_weight() before post_weight() reads it. weight/dtremain are not in restart files (OnePartRestart). The CPU behaves the same way: it leaves the slot's stale or memset contents. No reachable wrong result.
fix: none required. Optional hygiene: particle_kokkos.h:214 `OnePart tmp; tmp.dtremain = 0.0; tmp.weight = 1.0;` (or zero-init the struct).

### F-G13-2
VERDICT: REFUTED
reason: Slots [nlocal,maxlocal) are outside the live particle range. The CPU code also leaves stale data there: after post_weight deletions, or after compress/sort, those slots hold whatever particle was last moved out, so memset at grow time does not make them clean. Any later reuse of such a slot either overwrites every field (add_particle_kokkos plus explicit flag/dtremain/weight by callers, clone/memcpy, unpack in migrate) or reads only fields the caller fills; see F-G13-1 for the dtremain/weight consumers. Custom per-particle data is zeroed separately (zero_custom/zero_custom_kokkos). Copying garbage instead of stale data into dead slots changes no observable result.
fix: none required. Optional cost/hygiene tweak at particle_kokkos.cpp:812: copy only [0,nlocal), i.e. `Kokkos::deep_copy(Kokkos::subview(k_particles.view_device(),Kokkos::make_pair(0,nlocal)), Kokkos::subview(d_newparticles,Kokkos::make_pair(0,nlocal)));`

### F-G13-3
VERDICT: REFUTED
reason: The memset in CPU grow() only zeroes slots that have never been used. Slots that were reused after deletion or compression keep stale contents, which is why particle.cpp:730-731 marks the dependency with "??". No code path can rely on a fresh slot reading dtremain=0/weight=0. On every path, dtremain is read only for flags other than PKEEP, and those flags are set together with dtremain by the same caller (fix emit host paths, surf collide in update). Weight is reset by pre_weight() before post_weight() reads it, and surf products copy the parent's weight. read_restart unpacks OnePartRestart and then sets the remaining fields, and restart does not carry dtremain/weight. Custom attributes are zeroed by grow_custom (value-initializing resize). No reachable wrong result.
fix: none required. Optional parity fix at particle_kokkos.cpp:912: drop `Kokkos::view_alloc(Kokkos::WithoutInitializing)` from the Kokkos::resize, or zero the new range on device after the resize (`Kokkos::deep_copy(Kokkos::subview(k_particles.view_device(),Kokkos::make_pair(oldmax,maxlocal)), OnePart{})`). Either matches the CPU memset.

### F-G13-4
VERDICT: CONFIRMED
reason: remove_custom (particle_custom_kokkos.cpp:213-288) compacts ewhich[], eicol[] and edcol[], which are the host buffers of k_ewhich/k_eicol/k_edcol (grow_kokkos at lines 77/104/126). It only modify_host()/sync_device()s the four outer eivec/eiarray/edvec/edarray views. add_custom explicitly says "ewhich,eicol,edcol never modified on the device, so sync here" (lines 133-140). No other code ever syncs them: grep shows the only other syncs are in add_custom, and the init at lines 52-54 calls modify_host but never sync. The device copies are read in several places: copy_custom_kokkos (particle_kokkos.h:264,273), pack/unpack_custom_kokkos (particle_kokkos.h:364,382,405,423), zero_custom_kokkos (particle_custom_kokkos.cpp:318,340), and d_ewhich in collide_vss_kokkos.cpp (768, 1205, ...) and compute_tvib_grid_kokkos.cpp:123. With a separate device memory space (CUDA/HIP), the device keeps the pre-removal values. If the stale eicol is larger than the shifted array's real column count, the device reads and writes out of bounds. If it is smaller, columns are dropped and pack sizes no longer match the host-computed sizeof_custom. A stale d_ewhich makes collide/tvib index the wrong or an out-of-range eiarray entry. The path is reachable: a fix that owns a custom attribute (e.g. fix vibmode/ambipolar) is unfixed while another custom array remains, and a later run continues. Host-memory-only builds (Serial/OpenMP, where view_device aliases host) are unaffected. The CPU has no device copy, so the bug is Kokkos-specific.
cpu-also: no
fix: in ParticleKokkos::remove_custom, particle_custom_kokkos.cpp, next to the existing outer-view syncs at ~lines 278-287, add:
  k_ewhich.modify_host(); k_ewhich.sync_device();
  k_eicol.modify_host();  k_eicol.sync_device();
  k_edcol.modify_host();  k_edcol.sync_device();
(the same block as add_custom lines 133-140). Note that collide_vss_kokkos/compute_tvib_grid_kokkos re-fetch d_ewhich from k_ewhich.view_device() in their init/compute paths, so the synced values are picked up.
