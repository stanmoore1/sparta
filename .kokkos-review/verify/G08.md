### F-G08-1
VERDICT: CONFIRMED (low-med; silent wrong physics)
reason: Fix::style = verbatim arg[1] (fix.cpp:42-43), and explicit kk styles are documented as valid input (doc/Section_accelerate.txt:587-590). For `fix 1 vibmode/kk` / `fix 1 ambipolar/kk`, the strcmp at surf_collide_diffuse_kokkos.cpp:133/139 fails, so ambi_flag/vibmode_flag stay 0. The kernel then skips update_custom_kokkos (diffuse_kokkos.h:197-207) and surf_react_kokkos (215), and the kokkos_flag safety check is bypassed too. The CPU (surf_collide_diffuse.cpp:167) keys off modify->n_update_custom, which is independent of the style string. The same pattern is in all surf_collide_*_kokkos init() functions. It is the same root cause as F-G09-3 and F-G01-1.
cpu-also: no for surf_collide (the CPU uses the masks); the same style-string pattern appears in CPU collide.cpp:333 and react_bird.cpp:435
fix: in every surf_collide_*_kokkos.cpp init() (diffuse:133/139, specular, piston:~86/92, cll:133/139, td, impulsive, adiabatic), match `strcmp(style,"ambipolar")==0 || strcmp(style,"ambipolar/kk")==0`, and likewise for "vibmode"/"vibmode/kk". A cleaner option is a small shared helper, e.g. `static bool style_is(const char *style, const char *base)` that accepts base or base+"/kk". Apply it consistently with the F-G01-1 fix.

### F-G08-2
VERDICT: CONFIRMED (low; CPU parity)
reason: surf_collide_piston_kokkos.h:185-186 dereferences ip->x/ip->v right after react_kokkos (140-149), which can set ip=NULL. Piston does not forbid reactions (surf_collide_piston.cpp init only checks normals; doc/surf_collide.txt:110 says every style except vanish supports reactions), so `surf_react global/prob` with a delete or recombination channel on a piston face is reachable -> device null dereference. The secondary claim also holds: on the early `return NULL` (204-205/211-212) a jp created by the reaction (already counted in d_nlocal) is neither returned nor flagged PDISCARD, so it stays in the particle list unmoved. The CPU surf_collide_piston.cpp:140-178 has exactly the same code.
cpu-also: yes (src/surf_collide_piston.cpp:140)
fix: in both piston_kokkos.h (after line ~156, the react block) and surf_collide_piston.cpp (after line ~113), add `if (!ip) return jp;`, as the diffuse model does when it guards on `if (ip)`. Optionally, on the two "outside box" early returns, also discard jp (Kokkos: `if (jp) d_particles[jp - d_particles.data()].flag = PDISCARD;`; CPU: `if (jp) particle->nlocal--;`) so the reaction product is not orphaned.

### F-G08-3
VERDICT: CONFIRMED (med)
reason: SurfCollideVanishKokkos::collide_kokkos (surf_collide_vanish_kokkos.h:58-70) and the transparent model never write the `int &reaction` out-param. surf_collide_dispatch (update_kokkos.h:212-240) only forwards it, and UpdateKokkos::move declares `int reaction;` uninitialized per particle (update_kokkos.cpp:1209). So the value passed to the tallies (1861-1878) is garbage on a particle's first hit, or stale from an earlier reacting hit in the same move. Consumers that misbehave on a vanish surf (transparent=0, isr=-1):
- ComputeSurfKokkos ECHEM/ETOT (compute_surf_kokkos.h:406-411, 433-438) do KK_SR_TYPE(-1) -> OOB read of sr_type_list, then d_coeffs(reaction-1,1) OOB.
- ComputeSurfReactionTallyKokkos (compute_surf_reaction_tally_kokkos.h:84) records spurious reaction events with garbage REACTION ids. This also happens for transparent surfs, since it has no transparent test.
compute react/surf and react/isurf/grid are safe because they filter on isr match. The CPU has the same omission (update.cpp:578 `reaction` uninitialized; surf_collide_vanish.cpp / surf_collide_transparent.cpp never set it; compute_surf.cpp reads surf->sr[isr] with isr=-1).
cpu-also: yes
fix: set `reaction = 0;` at the top of collide_kokkos in surf_collide_vanish_kokkos.h:~64 and surf_collide_transparent_kokkos.h:~61, and in collide() of src/surf_collide_vanish.cpp:~43 and src/surf_collide_transparent.cpp:~45. The parameter is currently unnamed in the KK signature, so name it. Optional belt-and-braces: initialize `int reaction = 0;` at update_kokkos.cpp:1209 and update.cpp:578.
