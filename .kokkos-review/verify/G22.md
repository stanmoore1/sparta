### F-G22-1
VERDICT: CONFIRMED
reason: GridKokkos::id_find_child (src/KOKKOS/grid_kokkos.h:116-125) computes ix/iy/iz with the raw
inverse formula plus only `if (ix==nx) ix--`, whereas CPU Grid::id_find_child (src/grid_id.cpp:123)
calls id_point_child() (grid_id.cpp:39-77), which (a) re-derives the edges with the id_child_lohi master
equation and bumps ix-- if x<edge(ix) / ix++ if x>=edge(ix+1), then (b) clamps to [0,n-1]. The device
version IS used on the hot path: UpdateKokkos::move (src/KOKKOS/update_kokkos.cpp:2065 NPARENT, 2169
NPBPARENT) with x = face-exit point, exactly as CPU update.cpp:1413/1482. Where the difference matters:
the transverse coords of x landing on (or within an ulp of) an interior child boundary of the parent,
e.g. x[k] == lo + j*(hi-lo)/n exactly can give (x-lo)*n/(hi-lo) = j-eps -> j-1 on device but j on CPU
(">= lo, < hi" rule). Also the recursion into deeper levels uses the wrong child's lo/hi. Result: device
picks the neighbouring child (x on its boundary by round-off) -> divergence from CPU, possible
"particle outside cell" in grid/check, different cell-based tallies. Disproved parts of the claim: the
"-1 index / ichild wraps" scenario does not happen for round-off: static_cast<int> truncates toward zero,
so a tiny negative ratio gives 0, and a tiny overshoot of hi gives nx -> handled by ix==nx. Clamping only
matters for points far (>1 child width) outside the parent, which the callers never pass. So practical
impact is a rare boundary-round-off mismatch; severity low-med.
fix: src/KOKKOS/grid_kokkos.h:123-125 — replace the three `if (i==n) i--;` lines with the CPU
id_point_child logic (grid_id.cpp:55-76), e.g. for x:
`double edge = lo[0] + ix*(hi[0]-lo[0])/nx; if (x[0] < edge) ix--;`
`edge = lo[0] + (ix+1)*(hi[0]-lo[0])/nx; if (x[0] >= edge) ix++;`
`ix = MAX(ix,0); ix = MIN(ix,nx-1);` (same for y/z), or factor it into a KOKKOS_INLINE_FUNCTION
id_point_child in GridKokkos and call it (use Kokkos-safe max/min or ternaries on device).
cpu-also: no

### F-G22-4
VERDICT: CONFIRMED
reason: SurfKokkos::spread_inverse_custom (surf_custom_kokkos.cpp:562-567) just syncs host and calls
Surf::spread_inverse_custom (surf_custom.cpp:371-403). There: INT/DOUBLE array branches set
`in = &e?array_local[..][0][0]` guarded by `nown==0` and `out = &e?array[..][0][0]` guarded by
`size_custom_local==0` — guards swapped (compare spread_custom, surf_custom.cpp:358-362, which guards
owned by nown and local by size_custom_local). With nown>0 and nlocal+nghost==0 the local array is NULL
(surf_custom.cpp:353) -> NULL[0] deref segfault; with nown==0 the owned array is deref'd. DOUBLE vector

writes doubles over the edvec pointer table (heap corruption). Reachable: surf_react_adsorb.cpp:1258
(psflag, mode SURF, distributed surfs, on grid change). Additionally found in the same path
(surf_comm.cpp spread_local2own, n>1 branch): `idata = index * n` reads the LOCAL input with the OWNED
index; should be `isurf * n` (n==1 branch correctly uses isurf). Tau is an array of nactive_ps, so this
also corrupts values when nactive_ps>1. Not Kokkos-specific.
fix: src/surf_custom.cpp:383-386 and 395-398: `if (size_custom_local[index] == 0) in = NULL; else in =
&e?array_local[ewhich[index]][0][0]; if (nown == 0) out = NULL; else out = &e?array[ewhich[index]][0][0];`
src/surf_custom.cpp:390-391: pass `edvec[ewhich[index]]` (no `&`).
src/surf_comm.cpp spread_local2own (both INT and DOUBLE n>1 branches): `idata = isurf * n;`.

### F-G22-5
VERDICT: CONFIRMED
reason: fix_grid_check_kokkos.cpp:203-208 builds the error messages from host `particle->particles[i]`
(.icell, .id) and `grid->cells[icell].id` after the flags were computed from device data
(particleKK->sync(Device,...) at line 70 only). In a Kokkos run particles are moved on device, so host
particles are stale (last host sync); host icell may differ, giving wrong id/cell in the message, and a
stale icell (e.g. after grid shrink by adapt/balance, or -1) indexes cells[] out of bounds before
error->one. Only affects the error-mode diagnostics path; severity low.

pointers: `particleKK->sync(Host,PARTICLE_MASK); gridKK->sync(Host,CELL_MASK);` then
`auto cells = grid->cells; auto particles = particle->particles;`. Optionally guard the cells[icell]
reads with the IS_IN_INVALID_CELL check (it already error->one's first, so ordering is fine once synced).
