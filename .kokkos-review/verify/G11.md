VERDICT: CONFIRMED
reason: create_particles/kk IS instantiated: KOKKOS/create_particles_kokkos.h:17 registers `CommandStyle(create_particles/kk,CreateParticlesKokkos)` (installed via KOKKOS/Install.sh:180-181), and Input::execute_command (input.cpp:899-913) builds "<cmd>/<suffix>" and constructs `CreateParticlesKokkos cmd_obj` then calls `cmd_obj.command()` with -sf kk. The Kokkos class declares `create_local(bigint)` and `create_local_twopass(bigint)` (different signature, base not virtual) which only hide the base names in derived scope; the call inside CreateParticles::command binds statically to CreateParticles::create_local(). So the entire Kokkos body (create_particles_kokkos.cpp:52-464, including the recent fixes 40a10901/f8d576a8/95001c3c) is dead code; CPU CreateParticles::create_local (or create_local_twopass if `twopass` keyword given) runs. Impact is therefore: Kokkos path never executes (performance, and default (non-twopass) CPU RNG/placement order differs from the Kokkos/twopass order that create_particles.cpp:834 says is the Kokkos-compatible one). Severity med->low-med (no wrong output, but the style is a silent no-op).
fix: src/create_particles.h:65-66 -> `virtual void create_local();` `virtual void create_local_twopass();`. src/KOKKOS/create_particles_kokkos.h:33-34 -> `void create_local() override;` `void create_local_twopass() override { create_local(); }`. src/KOKKOS/create_particles_kokkos.cpp:52 -> `void CreateParticlesKokkos::create_local()` (drop the bigint param so `np` refers to the member, matching CPU create_particles.cpp:541/589 which sets member np, used by the nglobal-nprevious != np warning at create_particles.cpp:439).
