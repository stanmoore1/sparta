# Verify G19

### F-G19-1
VERDICT: CONFIRMED
reason: compute_fft_grid_kokkos.cpp:156-161 does Kokkos::deep_copy(d_array_grid,0.0) over every column. The K-space columns 0..startcol-1 are filled only in reallocate() (lines 402-474), which runs from post_constructor, init and rebalance, not on each compute. The CPU code zeroes only columns startcol..ncol-1 (src/FFT/compute_fft_grid.cpp:370-378). So with sum yes plus kx/ky/kz/kmag, the K columns read 0 after the first compute.
fix: compute_fft_grid_kokkos.cpp:160: replace `Kokkos::deep_copy(d_array_grid,0.0);` with `Kokkos::deep_copy(Kokkos::subview(d_array_grid,Kokkos::ALL(),std::make_pair(startcol,ncol)),0.0);`. This matches the CPU loop `for (m = startcol; m < ncol; m++)`.

### F-G19-2
VERDICT: CONFIRMED
reason: The member d_ingrid is set to k_ingrid.view_device() only in reallocate() (line 375). The compute and fix vector branches (lines 192, 222) reassign the member to the producer's d_vector_grid. The array branches (lines 195, 225) declare a local `auto d_ingrid = k_ingrid.view_device();` that shadows the member. The variable branch (~lines 238-242) only syncs k_ingrid. None of these branches points the member back at k_ingrid, and the d_ingrid_char/exchange_uniform at lines 248-250 reads the member. Take values c_a (a vector) then c_b[2] or v_g: the second FFT reads c_a's vector. In the CPU code every branch sets ingridptr (compute_fft_grid.cpp:401-435). This also happens on every later timestep, because the member persists.
fix: compute_fft_grid_kokkos.cpp:195 and :225: replace `auto d_ingrid = k_ingrid.view_device();` with `d_ingrid = k_ingrid.view_device(); auto l_ingrid = d_ingrid;` and write `l_ingrid[i] = ...` in the SPARTA_LAMBDA, which cannot capture the member. In the VARIABLE branch, after `k_ingrid.sync_device();`, add `d_ingrid = k_ingrid.view_device();`.

### F-G19-3
VERDICT: CONFIRMED
reason: ComputeFFTGridKokkos overrides post_constructor (line 99), so the base fft_create(), `memory->create(fft/fftwork)` and the base irregular setup never run. The base constructor leaves fft2d, fft3d, irregular1, irregular2, map1 and map2 NULL (compute_fft_grid.cpp:246-249), and `fft` is never allocated. The base ComputeFFTGrid::compute_per_grid uses irregular1->exchange_uniform, map1, fft, fft2d/fft3d and irregular2, so it dereferences NULL. That host path runs whenever prewrap==1, i.e. on any per-grid invocation before the first run/setup clears prewrap (update_kokkos.cpp:350-366). Examples are the adapt_grid command with c_ID (adapt_grid.cpp:774) and library extraction (library.cpp:492). Every normal path (dumps at setup, fix ave/grid during a run) happens after prewrap is cleared, so the trigger is uncommon. Severity is low to medium.
fix: compute_fft_grid_kokkos.cpp:125-126: replace the call to `ComputeFFTGrid::compute_per_grid();` with `error->all(FLERR,"Cannot (yet) invoke compute fft/grid/kk before the first run");`. Alternatively, drop the prewrap fallback and always call compute_per_grid_kokkos(), but that is unsafe, because input KK computes need wrapped device grid data.

### F-G19-4
VERDICT: CONFIRMED
reason: fft2d_kokkos.cpp:440 (mid_plan) and :463 (post_plan) pass `FFT_PRECISION,1,0,2` and `FFT_PRECISION,(permute+1)%2,0,2`, so nqty=FFT_PRECISION. FFT_PRECISION is 1 under FFT_SINGLE (spafftsettings.h:47). remap2d_kokkos ignores precision. With FFT_SINGLE, mid_plan therefore uses nqty=1 and unpack_2d_permute_1, and moves only one float per complex datum. pre_plan (:404) and all four fft3d_kokkos remaps (fft3d_kokkos.cpp:472,497,538,566) correctly pass `2,...,FFT_PRECISION`. The bug only shows in an FFT_SINGLE build. Severity is low.
cpu-also: yes. src/FFT/fft2d.cpp:247,282,306 pass FFT_PRECISION as nqty in all three plans.
fix: fft2d_kokkos.cpp:440: `2,1,0,FFT_PRECISION,`. fft2d_kokkos.cpp:463: `2,(permute+1)%2,0,FFT_PRECISION,`. This matches the fft3d_kokkos argument order.

### F-G19-5
VERDICT: CONFIRMED (latent)
reason: In the KISS branch of fft2d_kokkos.cpp, the slow-axis FFT runs out of place into a fresh d_tmp and then sets `d_data = d_tmp` (lines 302-309). d_out is written only by the post_plan remap (lines 315-322). post_plan is nullptr only when permute==1 and out == second layout (lines 451-455). In that case d_out still holds the mid-remap result (the mid_target==0 path) and the scaling functor scales it. The CPU code runs KISS in place, so data==out. This is unreachable from compute fft/grid/kk, which passes permute=0 (compute_fft_grid_kokkos.cpp:548-550), so post_plan always exists.
fix: fft2d_kokkos.cpp, KISS branch after line 309 (`d_data = d_tmp;`): add `if (!plan->post_plan) Kokkos::deep_copy(Kokkos::subview(d_out,std::make_pair(0,(int)((plan->total2)))),Kokkos::subview(d_tmp,std::make_pair(0,(int)plan->total2)));`. total2 is the number of complex values after the slow FFTs, which equals the out size when post_plan is null. Apply the same fix in fft3d_kokkos.cpp (see F-G20-2).

### F-G19-6
VERDICT: CONFIRMED
reason: fft_2d_destroy_plan_kokkos (fft2d_kokkos.cpp:652-685) handles the MKL_GPU, MKL, FFTW3/NVPL and KISS backends but has no CUFFT or HIPFFT branch. The plans created with cufftPlanMany/hipfftPlanMany at lines 598-618 are never destroyed. This leaks one set of plans and their work areas per FFT2dKokkos object, i.e. each time a compute fft/grid/kk instance is deleted and re-created. Severity is low.

### F-G19-7
VERDICT: CONFIRMED (low)
reason: With FFT_KOKKOS_FFTW_THREADS, create calls `fftw_init_threads` only if nthreads>1 (lines 563-567). destroy calls `fftw_cleanup_threads()` unconditionally (lines 670-672), even when init_threads was never called. The FFTW manual says that after fftw_cleanup/cleanup_threads all existing plans become undefined. Two live compute fft/grid/kk instances (or the 2D and 3D FFT objects), one of which is deleted, therefore leaves the other's plans undefined. fft3d_kokkos.cpp:700/848 has the same pattern. The trigger is rare.
fix: fft2d_kokkos.cpp:670-672 (and fft3d_kokkos.cpp:847-849): remove the `FFTW_API(cleanup_threads)();` call. Alternatively, guard it with a process-wide static reference count that both FFT2dKokkos and FFT3dKokkos increment at init_threads, and call cleanup only when the count reaches 0. Removing the call matches the CPU FFT code, which never calls init/cleanup.

### F-G19-8
VERDICT: REFUTED (main claim). A residual latent nit is noted below.
reason: With usecollective=1, nsend and nrecv include self, so plan->nrecv == nrecv. That makes `plan->self = 0` (line 406), and the self block in remap_2d_kokkos (line 152) is skipped, so there is no send_offset[nsend]/recv_bufloc[nrecv] out-of-bounds access. The self message goes through MPI_Send to self. All Irecvs, including self, are posted before any MPI_Send (lines 116-121), so the self send matches a pre-posted receive and cannot deadlock. The receive loop unpacks it once. The data path therefore works. What remains: remap_2d_destroy_plan_kokkos (line 456) reads plan->commringlen, which is never initialised (the plan is `new`ed). Under usecollective=1 a garbage value of 0 would only skip MPI_Comm_free, a comm leak. This is unreachable anyway, because compute fft/grid/kk forces collective_flag=0.
fix (optional nit): remap2d_kokkos.cpp after line 228: `plan->commringlen = 0;`.

### F-G19-9
VERDICT: CONFIRMED (code defect is real, but the stated scenario is wrong and the path is unreachable from compute fft/grid/kk today, so severity is low)
reason: unpack_2d_functor::operator() (pack2d_kokkos.h:115) does `d_buf[buf_offset + in] = d_data[data_offset + out];`. Here `in = slow*nstride+fast` is the strided data index and `out = slow*nfast+fast` is the contiguous buf index. The line both reverses the direction and swaps the indices. The CPU unpack_2d does `data[in++] = buf[out++]`, and the Kokkos unpack_3d (pack3d_kokkos.h:132) is correct. However, unpack_2d is used only by a permute==0 remap plan (remap2d_kokkos.cpp:334-335). The call paths in fft2d_kokkos.cpp: (a) pre_plan uses permute=0, but it is created only if some rank does not own the whole fast axis. In 2D, compute_fft_grid_kokkos.cpp:495-498 sets npx=1, so nxlo=0 and nxhi=nx-1 on every rank, remapflag=0 and pre_plan=nullptr. (b) mid_plan uses permute=1 (line 440), i.e. unpack_2d_permute_2 in double. (c) post_plan uses `(permute+1)%2` with permute=0 from compute (compute_fft_grid_kokkos.cpp:548-550), so its permute is 1 (unpack_2d_permute_2), not 0 as the finding claims. RemapKokkos2d has no other users in src/KOKKOS. So the broken functor is never hit by compute fft/grid/kk in any MPI configuration. It would be hit by any future caller with an fast-axis-split input or permute=1 output.
fix: pack2d_kokkos.h:115: replace the line with `d_data[data_offset + in] = d_buf[buf_offset + out];`.
